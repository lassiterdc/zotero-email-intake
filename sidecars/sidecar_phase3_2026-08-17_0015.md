#### Test failures and incomplete DoDs — mandatory two-option recovery framing (never-proceed-past rule)

When a halt is triggered by **either** of the following conditions, they are an absolute blocker to any further plan advancement:

- One or more failing tests ATTRIBUTED TO THIS PLAN — surfaced at QAQC time (Tier 1 `input needed` non-empty), at stop-gate evaluation (Tier 2 rubric), or mid-implementation. "Which tier of test" is irrelevant; red is red. Unit, integration, smoke, slow, fast, scoped, cross-cutting — all in scope. **Attribution is machine-produced and never agent-asserted, and a red that cannot be attributed is attributed to this plan by default**: the only admissible evidence that a red belongs to another branch is a `pwi_pytest_snapshot --delta ... --attribute` run exiting 0 with the nodeid printed on an `INHERITED` line, and its exits 4 (attribution unavailable) and 5 (probe not environmentally equivalent) are BLOCKING exactly like exit 1. This scopes the rule's subject; it does NOT add a third option. Nothing here permits presenting "proceed past" in any form, and an agent reasoning that a red "looks upstream" without the exit-0 artifact has asserted attribution rather than measured it. Each machine-classified `INHERITED` nodeid must be recorded as a cold-start-grade follow-up carrying `capture as idea + vote-bump to N` so upstream breakage is not silently normalized; each `INHERITED-STALE` nodeid is instead remedied by re-running the pre-compaction integration merge, which removes the red outright.
- One or more unmet Definition-of-Done items on the current phase or plan — whether measurement targets unmet (e.g., runtime target missed, coverage target missed), capability targets unmet (e.g., "all of X passes"), or artifact targets unmet (e.g., required doc sections missing, required outputs not generated).

The halt report must NOT offer the user any option that would close the current phase or advance to the next one while either condition holds. Specifically forbidden framings:

- "Proceed to next phase with failures/gaps as follow-up"
- "Accept current state and continue"
- "Capture failures/unmet DoD items as tech-debt and move on"
- "Commit partial progress and advance" (when framed as a path forward rather than as rescue-commit before fix work)
- "Proceed to `/wrapup-session`" (when failures or unmet DoD items remain)
- "Close this phase; revisit later" (the later revisit is an open-ended deferral without a fix commitment)

Silently closing a phase with red tests or unmet DoD converts a known, localized gap into a future archaeological dig. It is a category error — not a trade-off to weigh.

The halt report must present exactly two options:

- **Option A — Recommend specific fixes for user confirmation.** When the failures or unmet DoD items trace to identifiable root causes that you have enough context to propose concrete fixes for (e.g., a missing config field, an incorrect template ordering, a known toolkit defect with a narrow workaround, a missing assertion needed to meet a DoD checkbox), enumerate each fix as a specific proposal — naming the file, the defect or gap, and the exact change — and ask the user to confirm before applying. Vague proposals like "investigate X" or "look into Y" are not Option A; they are Option B.

- **Option B — Recommend plan mode for thorough investigation.** When the failures or unmet DoD items trace to root causes you do not yet have enough context to fix, or when multiple competing fix approaches need to be weighed, or when the fix would require cross-cutting changes (toolkit internals, multiple components, design trade-offs that affect the broader plan), recommend the user enter plan mode. Plan mode produces an investigation plan that the user then approves before any code changes happen.

Recommend exactly one of A or B with a one-sentence rationale grounded in the specific failure evidence or the specific DoD item that is unmet. Do not present a third "proceed past" option — not as the third bullet, not as an `AskUserQuestion` choice, not as "Other" escape-hatch framing. The never-proceed-past rule is not a default that users can override with a single message; it is a standing norm. If the user explicitly directs you to advance past red tests or unmet DoD, state that this violates the standing norm and ask them to confirm they want to override it before proceeding.

#### Release-readiness deferral prohibition (never-defer-a-broken-public-artifact rule)

This is the deferral-direction companion to the never-proceed-past rule above, and it is equally absolute — not a trade-off to weigh.

No deferral framing — "settle before announcement", "capture before the release is announced", "quick follow-on", "publication-readiness follow-up", "post-vX.Y.Z follow-up", "capture as idea", or any equivalent — may be used for an item whose non-resolution would ship a **silently-broken or misleading PUBLIC artifact** of the session's target outcome. Public artifacts include (non-exhaustively): a published package or wheel and its dependency metadata; the rendered documentation site; the README; a CITATION / DOI / release-notes record; and any CI status check whose green would be read as certifying something it did not actually exercise. Such an item is RELEASE-BLOCKING and in-scope; routing it to `# Follow-up Ideas` or an orthogonal-followup disposition IS the failure mode this rule exists to prevent — treat the urge to defer it as the tripwire, not as a resolution.

This binds even when the item is orthogonal to the immediate phase. **Orthogonality to the current phase NEVER overrides in-scope-ness for the session purpose:** an item that ships a broken public artifact of the release is in-scope for a session whose purpose is that release, however tangential it is to the phase in hand. (This is the halt-side statement of the `# Follow-up Ideas` dual-orthogonality precedence rule; the follow-up-ideas atomics carry the routing-side statement.)

**Named mechanism (RLHF).** Two pulls manufacture the deferral. Task-completion bias makes closing the visible phase feel like progress, so a release-blocking defect that is inconvenient to fix now gets relabeled a "follow-up." Fresh-agent-deferral bias makes handing the defect to a later or post-release agent feel helpful — but that agent has less context, and for an immutable artifact (a published wheel, a minted DOI) often no ability to fix it at all, because there is no "after". Recognize both pulls as the mechanism firing, not as a signal that deferral is appropriate.

**Empirical anchor (this rule was written from a live near-miss).** On a first-public-release session, a specialist routed a broken-environment defect — a `pip install` that silently resolved an unvalidated, potentially heap-corrupting dependency stack — to `# Follow-up Ideas` as "a publication-readiness concern to capture before the release is announced." It was rejected: the defect was baked into an immutable PyPI wheel, so "fix it after the release" did not exist as an option. The dual-orthogonality criterion had been satisfied against the *phase* while violated against the *session purpose* (ship a working release). That is the exact failure this prohibition forecloses.
