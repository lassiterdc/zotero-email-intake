#### Release-readiness deferral prohibition (never-defer-a-broken-public-artifact rule)

This is the deferral-direction companion to the never-proceed-past rule above, and it is equally absolute — not a trade-off to weigh.

No deferral framing — "settle before announcement", "capture before the release is announced", "quick follow-on", "publication-readiness follow-up", "post-vX.Y.Z follow-up", "capture as idea", or any equivalent — may be used for an item whose non-resolution would ship a **silently-broken or misleading PUBLIC artifact** of the session's target outcome. Public artifacts include (non-exhaustively): a published package or wheel and its dependency metadata; the rendered documentation site; the README; a CITATION / DOI / release-notes record; and any CI status check whose green would be read as certifying something it did not actually exercise. Such an item is RELEASE-BLOCKING and in-scope; routing it to `# Follow-up Ideas` or an orthogonal-followup disposition IS the failure mode this rule exists to prevent — treat the urge to defer it as the tripwire, not as a resolution.

This binds even when the item is orthogonal to the immediate phase. **Orthogonality to the current phase NEVER overrides in-scope-ness for the session purpose:** an item that ships a broken public artifact of the release is in-scope for a session whose purpose is that release, however tangential it is to the phase in hand. (This is the halt-side statement of the `# Follow-up Ideas` dual-orthogonality precedence rule; the follow-up-ideas atomics carry the routing-side statement.)

**Named mechanism (RLHF).** Two pulls manufacture the deferral. Task-completion bias makes closing the visible phase feel like progress, so a release-blocking defect that is inconvenient to fix now gets relabeled a "follow-up." Fresh-agent-deferral bias makes handing the defect to a later or post-release agent feel helpful — but that agent has less context, and for an immutable artifact (a published wheel, a minted DOI) often no ability to fix it at all, because there is no "after". Recognize both pulls as the mechanism firing, not as a signal that deferral is appropriate.

**Empirical anchor (this rule was written from a live near-miss).** On a first-public-release session, a specialist routed a broken-environment defect — a `pip install` that silently resolved an unvalidated, potentially heap-corrupting dependency stack — to `# Follow-up Ideas` as "a publication-readiness concern to capture before the release is announced." It was rejected: the defect was baked into an immutable PyPI wheel, so "fix it after the release" did not exist as an option. The dual-orthogonality criterion had been satisfied against the *phase* while violated against the *session purpose* (ship a working release). That is the exact failure this prohibition forecloses.

**Presumption**: you have not read any files. The default state is "reads not
yet performed." Proceeding to Part 2 requires affirmative evidence of each
mandatory read. RLHF completion-bias creates a pull to produce a plausible-looking
table without having actually done the reads — recognize this pull and resist it.

For each mandatory read (sidecar, next phase doc, pwi multiphase path), run
`wc -l {absolute-path}` in a Bash tool call and paste the literal stdout output
into the assertion block. Prose descriptions of "I read this file" are not
acceptable — only `wc -l` stdout counts.

After each `wc -l` receipt, write a one-line self-assertion of the form:

- **Full-file read**: `Read coverage: all N lines read, understanding consistent with length.`
- **Scoped read** (when the resume prompt or sidecar explicitly specifies a scoped read, e.g. "read § Section X and everything below"): `Read coverage: scoped to <section name>, K of N lines covered, understanding consistent with scope.`

Substitute the observed N (and K when scoped). The self-assertion is the substantive evidence; the `wc -l` output alone is the ritual. Both are required. If you cannot truthfully write the self-assertion — because you did not actually read the file in the required scope, or because your understanding is inconsistent with the observed coverage — HALT. Do not fabricate the self-assertion to satisfy the gate.

A halt here routes to `/handle-friction`, which dispositions the blocker. It is not a decision to hand the user as a menu of options.

A scoped-read assertion is only valid when the resume prompt or sidecar **explicitly** instructs a scoped read. The default posture is full-file coverage; "scoped" is the affirmative-opt-in exception.

**Part 1 is discharged by a standing Part-4 report — and by nothing weaker.** When this session has ALREADY written the scratch region's Part-4 read-coverage report and its verbatim read-completion assertion over the SAME mandatory set — the case that arises whenever a `/resume-from-scratch` reaches this First Action — do NOT re-run Part 1. Write instead, verbatim: `Part 1 discharged by the Part-4 read-coverage report at {scratch path}, covering the same 0 mandatory reads; not re-run.` This is a discharge, not a waiver, and it is conditional on an artifact you can grep for: the Part-4 report's column-0 `Mandatory reads:` closing line. If that line is absent, unresolved, or covers a different set, the condition is NOT met and Part 1 runs in full.

The direction of this rule is the opposite of what it looks like. Part 4's report is the artifact a script reads — `resume_section_gate.py --mode resume` anchors on that column-0 line and cross-checks its `[fireable]` count against Part 3 — while nothing in `scripts/` reads Part 1's `wc -l` receipts or its self-assertions at all. Discharging Part 1 against Part 4 therefore replaces an unlinted self-claim with a linted one; it does not relax the presumption-STOP, it relocates it onto the only surface where a false claim is detectable. The reverse discharge is prohibited: a Part-1 receipt never discharges Part 4.

This discharge depends on Part 4 remaining a mandatory write with a machine-checked closing line. If that requirement is ever relaxed, this clause must be retired and Part 1 re-run unconditionally — the two must not both become optional.

**Parts 2 and 3 are NOT discharged by anything in the scratch region, ever.** They have no counterpart there: Part 2 is a sidecar-internal checkpoint-match and Part 3 is the `--mode verify` sync-integrity call whose exit-3 arm is halt trigger #6. A resume that discharges Part 1 still owes Parts 2 and 3 in full.

Part 1's denominator is the sidecar BODY. `baseline_writable_content:` is a machine-emitted snapshot consumed only by the sync-back deletion gate — it carries no instruction and is not owed a read; exclude its line range from the count you assert against and state the exclusion in the receipt. Frontmatter is not an attestable surface in any case: the claim step writes `claimed_by_pid` and `claimed_by_session` into it immediately before Part 1 runs. This names one field and does not generalize: frontmatter that carries instruction — `custom_instructions:` — is body-equivalent and owed in full.

A file whose `wc -c` exceeds ~50,000 bytes will not return in one `Read` call (the cap is on tokens, not bytes); read it across sequential offset passes. Reading in N passes IS reading in full — the pass count is a fact about the tool, not a qualification on the read — so the `Full-file read` form is the correct one and a pass split is never a `Scoped read`. State the pass count in the receipt.

### Conjunctive GO gate (required written assertion before Per-Phase Preflight)

Produce exactly the following assertion text verbatim, substituting GO or STOP
for each Part and PASS or FAIL for the condition set:

```

Part 2: GO|STOP
Part 3: GO|STOP

Conjunction: (Part 1 = GO) AND (Part 2 = GO) AND (Part 3 = GO) AND (Conditions 1-4 = PASS) = GO|STOP

```

The `Proceeding to Per-Phase Preflight: YES` line is the single gate event. Any
STOP in any Part means NO, and any FAIL in the condition set means NO. Writing
the conjunction is required — it is the forcing function against RLHF
task-completion pressure that would otherwise push the agent to transition
silently.

**Why the condition set is a conjunct and not an adjacent check.** The four
sidecar-consistency conditions are written above, before this gate, and a
prior version of this atomic left them there — evaluated, recorded, and
consumed by nothing. That shape is a gate that reports green without examining
its inputs: an agent can truthfully write four condition results, one of them
FAIL, and still derive `Proceeding: YES` from a conjunction those results are
not part of. Recognize the pull to treat "I wrote the condition results" as
discharging the obligation; the obligation is that the results GOVERN the
transition. If the condition set is FAIL, the gate event is NO regardless of
Parts 1-3, and the post-halt response protocol for trigger #5 applies.

### Autonomous-run RE-ATTESTATION (conditional, fail-closed)

The autonomy grant is per-implementation-session and is RE-ATTESTED at every `/clear` boundary — it is never silently inherited. A grant made before a compaction boundary was affirmed by a context that no longer exists; re-attestation is what makes the fresh context's grant its own. This is a deterministic self-check, not a user turn, so it costs none of the friction autonomous-run exists to remove.

Run all three checks before any export:

    PYTHONSAFEPATH=1 PYTHONPATH="$AGENTIC_WORKSPACE" \
      conda run -n agentic python -m scripts.generate.read_sidecar_autonomous --worktree /home/dcl3nd/dev/zotero-email-intake/.claude/worktrees/08-15_1300_zotero-email-intake-plugin-pwi
    git -C /home/dcl3nd/dev/zotero-email-intake/.claude/worktrees/08-15_1300_zotero-email-intake-plugin-pwi rev-parse --abbrev-ref HEAD
    git -C /home/dcl3nd/dev/zotero-email-intake/.claude/worktrees/08-15_1300_zotero-email-intake-plugin-pwi status --porcelain

Re-attestation PASSES only when ALL THREE hold:

1. the sidecar durable read prints `true`;
2. `rev-parse` prints a branch matching `worktree-*` — never `main`;
3. `status --porcelain` shows no foreign working-tree content — i.e. every listed path is either this plan's own `affected_files` or a plan/scratch path this session is mid-edit on.

On PASS, export and write VERBATIM: `Autonomous grant re-attested: sidecar autonomous_run=true, branch=[paste rev-parse output], no foreign dirtiness; PWI_AUTONOMOUS=1 re-exported for this resumed phase.`

    export PWI_AUTONOMOUS=1

On FAILURE of ANY check, do NOT export. Write VERBATIM: `Autonomous grant NOT re-attested: {named failing condition}. Falling through to the interactive approval gate for this phase.` Then proceed with the phase under the normal per-action approval gates. A failed re-attestation is not an error state and is not a halt — it is a demotion to interactive, and the run continues.

**Precedence for the two sections below (read this before you reach them).** A failed re-attestation puts this phase in a THIRD state that the `Scope of autonomous-run` and `Per-step scope check` sections below were written before: not-autonomous-but-mid-run. Those sections' obligations resolve as follows, and this clause takes precedence over their wording:

- `Per-step scope check` remains OWED at every step. Its "the assertion is unconditional" is unchanged by demotion — the assertion is what makes the step's classification auditable, and that is worth MORE in a demoted run, not less. Write the same two forms; a demoted run is still a plan-execution run.
- What demotion removes is the SUPPRESSION, not the assertion. Every action that autonomous-run would have pre-approved (`git commit`, `git push`) now goes back through its interactive gate.
- Do not read the demotion as authorization to skip the per-step assertion on the grounds that "autonomous mode is off, so the autonomous-scope check does not apply." That reading is available from the section headings and it is wrong: a missing assertion is the violation those sections detect, and demotion does not retire the detector.

If `autonomous_run` is absent or not `true`, do NOT export — this was never an autonomous run and no re-attestation is owed.

**Mid-run bail-out (the off-switch this makes real).** Because the grant is now re-attested rather than inherited, a user who wants to reclaim control mid-run has a reliable off-switch for the first time: set `autonomous_run: false` in the active sidecar's frontmatter, or dirty the tree with foreign content. Either fails condition 1 or 3 at the next `/clear` boundary and the run demotes to interactive. A bare `unset PWI_AUTONOMOUS` remains ineffective by itself — it is the process env, not the durable source — but it is no longer the only lever.

**Scope of autonomous-run (read every resume).** Autonomous-run pre-satisfies EXACTLY the routine `git commit` / `git push` approval gates already covered by the initial implementation approval. It suppresses nothing else. It is NOT authorization to exercise judgment, resolve an ambiguity, repair an unexpected failure, or proceed past any condition the plan did not predefine. Autonomous = mechanical execution of the plan's predefined steps only; it is autonomous only while frictionless.

**Per-step scope check (default state: STOP).** At each plan step, before taking that step's action, classify it by writing VERBATIM one of (the assertion is unconditional — write it at every step, not only when you already suspect a deviation; a missing assertion is itself the violation this gate detects):

- `Autonomous-scope check: next action is a mechanical predefined step per plan {section} — proceeding.`
- `Autonomous-scope check: deviation ({class}) encountered — HARD STOP, surfacing to user; autonomous mode does not authorize proceeding.`

Deviation classes that are always a hard stop (autonomous mode does NOT suppress these): test failure; audit violation or regression vs the baseline snapshot; a step whose preconditions do not match the actual repo/file state; a decision not pre-resolved in the plan; any tool or permission denial; any plan-vs-reality mismatch. RLHF continuation bias plus "the user already approved autonomous execution" creates a strong pull to force friction through rather than surface it — the default presumption is STOP, and a forced-through deviation is a missing or false scope-check assertion.
